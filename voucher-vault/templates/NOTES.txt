  Then open http://127.0.0.1:8000/ — not http://localhost:8000/. Only 127.0.0.1

  CSRF_TRUSTED_ORIGINS holds exactly http://127.0.0.1:8000, so any other local
  port fails every POST including the login form.

THE FIRST START PRINTS THE ONLY ADMIN PASSWORD IT WILL EVER PRINT
  Against an empty database the entrypoint creates the superuser "admin" with a
  randomly generated password and writes it to stdout — once, never again, and
  into no Secret:

    kubectl -n {{ .Release.Namespace }} logs {{ $pod }} | grep -A3 "Creating superuser"

  If that line has already scrolled out of the log, reset it in place:

    kubectl -n {{ .Release.Namespace }} exec -it {{ $pod }} -- python manage.py changepassword admin

  With OIDC enabled the app drops its password-change pages and the login form
  redirects to the provider on its own (OIDC_AUTOLOGIN). Django's own admin
  login at /admin/ is not covered by that redirect — that is the way back in
  when the provider is down or its item is wrong.

A POD THAT NEVER STARTS IS USUALLY WAITING FOR POSTGRES
  Before it opens the HTTP port, the entrypoint loops on
  "nc -z $POSTGRES_HOST $POSTGRES_PORT" with no timeout. A wrong host or port in
  the database item therefore produces no error at all — the log simply stops at

    [TASK] Waiting for PostgreSQL db...

  until the startup probe kills the container. That budget is
  {{ $startup.periodSeconds }}s x {{ $startup.failureThreshold }} failures = {{ mul $startup.periodSeconds $startup.failureThreshold }}s, and it surfaces as CrashLoopBackOff.

  The other candidate is one line earlier: the entrypoint exits 1 with "[FAIL]
  Insufficient permissions on bind mount volume" when /opt/app/database is not
  writable for uid/gid 33. fsGroup 33 covers that on
  {{ if .Values.storage.storageClass }}storage class "{{ .Values.storage.storageClass }}"{{ else }}the cluster's default storage class{{ end }}, as long as it honours fsGroup.

WHAT A READY POD DOES NOT PROVE
  The probes send "Host: 127.0.0.1" on purpose: that host is always in
  ALLOWED_HOSTS, so probing survives every domain change. The price is that a
  wrong ingress.domain is invisible to Kubernetes — all three probes pass, the
  rollout goes green, and every real request gets 400. Check it against the
  domain instead:
{{ if .Values.ingress.enabled }}
    curl -sI https://{{ .Values.ingress.domain }}/ | head -1
{{- else }}
    curl -sI http://127.0.0.1:8000/ | head -1     # through the port-forward above
{{- end }}

  A 302 to a language-prefixed path is the healthy answer; 400 means the Host
  does not match. Celery is the second blind spot: worker and beat are started
  detached from the same entrypoint, so uwsgi answers whether or not they came
  up. A wrong redis-url costs the expiry notifications and shows nothing else.

THIS RELEASE IS SINGLE-INSTANCE BY CONSTRUCTION
  Uploaded files land in /opt/app/database, on the one ReadWriteOnce PVC
  {{ .Release.Name }}-{{ .Chart.Name }}-pvc ({{ .Values.storage.amount }}),
  which every pod of the StatefulSet mounts at the same path — and each pod runs
  its own Celery beat. Raising voucherVault.replicas above 1 therefore buys
  nothing: further pods stay Pending on a node that does not hold the volume,
  and where they do start they send every expiry notification a second time.

UPGRADES MIGRATE, ROLLBACKS DO NOT UNMIGRATE
  Every single start runs makemigrations and migrate before the server comes up,
  so an app-version bump changes the schema the moment the new pod boots.
  "helm rollback" puts the old image back but leaves the migrated schema in
  place, and the old code then meets columns it does not know. Back up before
  bumping the app version, and back up both halves: the rows live in Postgres,
  the uploads on the PVC.

EXPIRY NOTIFICATIONS STAY SILENT UNTIL A USER ADDS AN APPRISE URL
  EXPIRY_THRESHOLD_DAYS ({{ index $env "EXPIRY_THRESHOLD_DAYS" | default 30 }}) and EXPIRY_LAST_NOTIFICATION_DAYS ({{ index $env "EXPIRY_LAST_NOTIFICATION_DAYS" | default 7 }})
  decide when an item counts as expiring, not whether anyone hears about it:
  delivery runs over the Apprise URLs each user stores in their own profile, and
  a profile without one is skipped without a word. The "Periodic Expiry Check"
  schedule runs daily at 09:00 in the container's time zone
  (TZ={{ index $env "TZ" | default "Europe/Berlin" }}) and is created ONLY while an empty database is initialized —
  delete it in the admin and no later start brings it back.
